01

背景与目的

Background & Purpose

我司实行「自研产品 + 客户 OEM/ODM」双轨业务。当前某客户项目需向客户输出《产品规格书》，但内部对由谁主导编制、如何组织评审、由谁批准、客户提供的规格书如何引用存在争议，流程尚未统一，存在返工与口径不一致风险。

本文件目的

  • 统一产品规格书从需求输入 → 编制 → 评审 → 批准 → 受控 → 变更的全流程，明确各环节主责部门与参与部门；
  • 厘清自研产品与客户 OEM/ODM 项目两种模式下规格书定位与审批链的差异；
  • 给出争议焦点问题的建议口径，供内部讨论拍板，最终形成受控管理文件。

三条基本原则

原则一 · 主笔负责
谁编写条款，谁对条款的技术与质量负责；跨专业条款必须由对应专业部门主笔，不允许单人闭门定稿。
原则二 · 会签评审
规格书是产品开发与客户确认的基准文件，关键条款须经研发、工程、品质、采购、生产、财务等多部门评审会签。
原则三 · 先批后用
规格书批准发布前，不得作为打样、开模、采购、试产的依据；发布后任何变更必须走受控变更流程，严禁口头变更。
02

术语与文档关系

Terms & Document Hierarchy

核心术语

  • 产品规格书（PS, Product Specification）：定义产品功能、性能、结构、材料、安全、法规、包装等要求的受控文件，是产品开发、检验、采购、生产与客户确认的基准文件。
  • 客户需求文件：客户提供的需求输入（RFQ、需求表、客户版规格书、口头/邮件需求），属「输入文件」，需转化为内部规格书，不得直接作为内部开发与检验依据。
  • 需求覆盖矩阵：将客户每一条要求与内部规格书条款逐一映射，标注「满足 / 协商 / 超出 / 不适用」的对照表，是客户项目评审与验收的依据。
  • ECR / ECN：工程变更申请（Engineering Change Request）/ 工程变更通知（Engineering Change Notice），规格书变更的受控载体。

规格书在文件体系中的位置

立项书 / 产品定义
回答 Why（为什么做）
→
产品规格书 ★
回答 What（做什么、做到什么程度）
→
技术方案 / 开发任务书
回答 How（怎么做）
→
检验规范 / 测试报告
回答 Verify（如何验证）

规格书是承上启下的基准：上游承接立项书与客户需求，下游约束技术方案、检验规范、采购与生产。规格书一旦失准，下游全部失真。

关键判断
无论哪种模式，规格书都是同一份受控文件，差异只在「触发、牵头、评审重点、批准链」四个维度。建议共用一套流程模板，用「项目类型」字段区分走哪条分支，避免两套流程打架。

06

争议焦点与处理建议

Disputes & Recommendations
?争议一：产品规格书到底由哪个部门编制？
争议源于「编制」被理解为单一部门的事。建议采用「牵头 + 主笔 + 会签」三级协作机制，而不是指定一个部门全权负责：
  • 牵头：产品部（自研）/ 项目部（客户项目，管进度与客户接口）——负责组织、排期、汇总、裁决；
  • 主笔：产品部写产品定义类条款，研发部主笔技术条款，工程部、品质部、采购部分别补充结构/工艺、质量/认证、物料条款——谁的专业谁写；
  • 会签：草案提交各部门按专业维度评审会签，通过后由批准人定版。
结论：规格书是「产品部牵头、研发部主笔、多部门会签」的集体产物，单一部门包办既不合理也不可行；客户项目由项目部牵头组织，避免产品部孤军作战。
?争议二：客户给了规格书，能不能直接引用、直接用？
不能直接用。客户规格书是「需求输入」，缺内部工程实现、检验标准、公差与认证细节，直接引用会在开发与检验环节产生真空。
客户规格书 / RFQ
需求输入
→
需求解析 + 条款映射
需求覆盖矩阵
→
内部产品规格书
客户要求 + 工程实现 + 检验标准
结论：客户规格书须转化为内部规格书，并通过需求覆盖矩阵逐条映射（满足 / 协商 / 超出 / 不适用）；转化后原客户要求仍保留原文备查，作为验收依据。
?争议三：评审会由谁主持？规格书由谁批准？
  • 评审主持：自研 = 产品部；客户项目 = 项目部（可邀请产品部提供产品专业支持或联合主持）；
  • 内部批准：自研 = 产品部负责人；客户项目 = 项目部负责人——批准人对规格书与输入的一致性负最终责任；
  • 外部确认：客户项目必须经客户签认 / 邮件确认后方可进入开发执行阶段。
结论：「谁组织评审」与「谁批准」分离——组织者负责流程与进度，批准人承担文件责任；客户项目双确认（内部批准 + 客户确认）缺一不可。
?争议四：规格书和报价、立项是什么关系？会不会拖慢报价？
规格书编制与商务报价可以并行推进，不必串行等待：
  • 报价阶段：业务部接 RFQ 后，研发 + 采购 + 财务基于初步需求做粗成本测算，支撑报价——此时无需完整规格书；
  • 立项 / 合同阶段：规格书草案（V0.x）可作为合同技术附件的底稿，随合同签署同步完善；
  • 开发阶段：规格书正式版（V1.0）作为项目基线，冻结后方可打样 / 开模 / 采购 / 试产。
结论：报价用「粗测算」、合同用「草案」、开发用「正式版」——三个时点三种颗粒度，规格书流程不阻塞报价，反而为报价提供依据。
?争议五：规格书批准后还能改吗？口头改行不行？
可以改，但必须走受控变更。规格书冻结后即成为项目基线，任何调整（哪怕是客户口头要求）都必须：
  • 提出部门提交 ECR → 产品部组织 ECN 评审（评估技术 / 成本 / 交期 / 质量影响）→ 按变更分类审批（见 08 节）；
  • 客户项目涉及客户要求的变更，须客户书面再确认（邮件 / 签认）后方可实施；
  • 版本升级并登记修订记录，新版分发、旧版回收。
结论：规格书「可改、必受控」。口头变更不更新文件，是开发返工、成本超支、客诉纠纷的第一源头，应列入红线禁止。

08

变更管理细则

Change Control

变更触发源

客户需求变化 ｜ 技术障碍 ｜ 物料停产或替代 ｜ 法规 / 认证更新 ｜ 成本压力 ｜ 生产品质问题 ｜ 设计优化

变更分类与审批规则

分类变更情形审批要求
A 类影响客户需求 / 合同约定 / 法规认证的变更（功能增减、关键性能、认证范围）ECR → ECN 评审 → 客户书面确认 → 产品部 / 项目部批准 → 发布新版
B 类影响性能 / 成本 / 交期但未涉及客户约定的变更（材料替代、工艺调整、结构优化）ECR → ECN 评审 → 产品部 / 项目部批准 → 发布新版（客户项目视合同约定通报客户）
C 类编辑性修改（勘误、格式、措辞，不影响技术内容）修订记录直接更新，产品部确认后发布新版

时限建议

  • ECR 受理：1 个工作日内由产品部确认受理并指派评审组织人；
  • ECN 评审：3 个工作日内完成（A 类可延长至 5 个工作日）；
  • 需客户确认的变更：按客户约定时限跟踪，闭环记录确认结果，禁止先动后报。
红线（不可逾越）
① 严禁口头变更、严禁未批先动（未批准先改模 / 先采购 / 先投产）；
② 变更必须更新版本号与修订记录，新版发布、旧版回收；
③ 客户项目涉及客户要求的变更，必须客户书面确认（邮件 / 签认），微信口头确认不作为依据。

一页速查

Cheat Sheet
谁写？
牵头：产品部（自研）/ 项目部（客户项目）
主笔：产品部（产品条款）+ 研发部（技术条款）+ 工程 / 品质 / 采购（专业条款）
机制：谁的专业谁写，多部门会签
谁审？
组织：产品部（自研）/ 项目部（客户项目）
会签：研发 · 工程 · 品质 · 采购 · 生产 · 财务 · 业务
关口：评审不通过不得进入批准
谁批？
自研：产品部负责人
客户项目：项目部负责人（内部）+ 客户确认（外部）
定版：文控编号，V1.0 受控发布

五阶段主线

需求输入（业务部 / 产品部）→ 规格书编制（产品部牵头 · 研发部主笔）→ 内部评审（多部门会签）→ 批准发布（内部批准 + 客户确认）→ 受控分发与变更（文控受控 · ECN）

客户项目三个「必须」

  • 必须做需求覆盖矩阵：客户条款逐条映射到内部规格书条款；
  • 必须客户书面确认：规格书定版前与涉及客户要求的变更时；
  • 必须先批后用：未批准的规格书不得作为打样、开模、采购、试产依据。
