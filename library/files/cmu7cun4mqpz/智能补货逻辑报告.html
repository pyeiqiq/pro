1. 摘要（Executive Summary）

智能补货模块回答一个运营最关心的问题：「当某 SKU 需要补货时，应该补多少、最晚什么时候下需求单？」 它不做静态的安全库存点估算，而是把「在库 + 在途 + 已下需求」拆成 7 个到货阶段（A–G），叠加到「今天起 100 天」的逐日销量消耗上，跑一遍逐日滚动模拟，从而同时给出：首次缺货日、可售天数、100 天总缺口、以及在「补货视界 N 之后」的累计缺货量（即建议补货量）。

给「人」看（专业介绍）

  • 跨 6 个模块的单一事实源（Single Source of Truth），不另存副本；
  • 计划 / 实际双销量维度对照，避免单看一个点估算误导；
  • 「可售天数预测」总表 + 单 SKU 100 天趋势图（黄线库存、绿柱到货、红虚线缺货日）；
  • 库存趋势导航：一键在真正缺货的 SKU 间按维度切换；
  • 一键倒推生成带回交期与补偿量的补货需求单。

2. 背景与要解决的问题

传统补货常用「当前库存 ÷ 日均销量 = 可售天数」做点估算，其缺陷在跨境电商场景下被放大：

痛点传统做法的盲区本模块如何解
到货是分批、滞后的把在途/已下需求笼统当一个数字，看不到「哪天到、到多少」拆成 A–G 七阶段，每阶段带 etaDays（距今天到货天数）逐日注入
销量是逐日波动的用月均日销量抹平波动，会误判缺货时点消耗按销售计划逐日映射（计划维度）或近 30 日扁平均（实际维度）
补货有固定前置工期不知道「今天不下单，N 天后才到」意味着 N 天内缺口已发生定义补货视界 N，建议补货量只统计 d ≥ N 之后的累计缺口
数据散落在多系统人工拼 M2 采购、M3 库存、M4 物流、M5 需求单统一从各模块 localStorage 单一事实源同步读取，零手工拼表
结果不可执行算出一个数字但不知怎么落地成采购动作一键倒推工厂交付 ETA 并生成「已通过」补货需求单推送 M2

3. 总体架构与数据来源

模块遵循项目「单一事实源」纪律：上游模块是唯一数据拥有者，智能补货只读不存副本。读取在 syncCatalog()（商品/MODEL/描述）与计算时直接 loadM3()/loadM2()/loadM4()/loadM1()/loadMaster() 拉取。

4. 核心概念

4.1 补货视界 N（Reorder Horizon）

从「今天下需求单」到「该批货入亚马逊仓可售」所需的最少天数，由三段工期相加：

N = produce（生产） + sea（海运） + portIn（到港入仓） 默认参数：produce=25, sea=30, portIn=10 → N = 65 天

含义：今天下的单，最早第 N 天才能补上库存。因此「建议补货量」只统计第 N 天之后的缺口——N 天内的缺口只能靠现有在途/在库硬扛。

4.2 七项进项阶段 A–G（Inbound Stages）

把「未来会进来、能卖给客户的货」按到达亚马逊仓的先后与来源拆成 7 段。每段给出数量 qty 与到货天数 etaDays（距今天）。

阶段名称数据来源etaDays（到货天数）
A亚马逊在库M3 亚马逊仓净库存0（当下即可售）
B第三方仓库存M3 第三方仓(pl)净库存transfer3pl（默认 10）
C在途数量M4 头程未结运单（按剩余量分摊）max(0, daysBetween(今天, eta))
D物流仓数量M3 物流仓净库存sea + portIn（默认 40）
E供应商仓库存M3 供应商仓净库存3 + sea + portIn（默认 43）
F未入库数量M2 采购订单(进行中) 未收量取 delivery_time；无则 = N
G已下需求M5 已通过需求单合计produce + sea + portIn = N

4.3 进项合计 J

J = A + B + C + D + E + F + G

J 是「未来 100 天内可售的总供给量」的近似（其中 A 当下即可售，其余按到货日注入模拟）。它是衡量是否缺货的分母。

4.4 两个销量维度

维度 dim消耗来源逐日取值方式
plan 计划每日销量销售计划（M5 sales_plans）按日期映射到该月销售计划的当日值；当日缺失则回退该 SKU 全部计划日均值；全无计划→0
avg 实际每日销量实际销量（M5 sales_actuals）近 ≤30 日实际销量求均值（扁平均），100 天全部用该值；无实际→0（不做增长率外推）

实际维度刻意采用「近 30 日扁平均」而非增长率外推：增长率在销量波动场景下会无限放大，数值失真。两个维度各跑一遍模拟，互为对照。

5. 计算公式全集

约定：d ∈ [0, 99] 表示距今天第 d 天（d=0 为今天）；T0 = 今天（本地日期）；所有库存、数量单位均为「件」。

5.1 A–G 与 J

A = m3Stock(code,'amazon') m3Stock(code,wh) = Σ inbound_qty(wh) − Σ outbound_qty(wh) + Σ qty_delta(wh) // 来自 erp_m3_v1 B = m3Stock(code,'pl') C = Σ_event qty // 来自 erp_m4_v1 头程在途剩余（结单/异常不计），按运单剩余量比例分摊到 SKU D = m3Stock(code,'logistics') E = m3Stock(code,'supplier') F = Σ_{po∈进行中} max(0, item.qty − 已入仓量) // 来自 erp_m2_v1 G = Σ_{r∈已通过需求单} item.qty // 来自 erp_m5_v1 requisitions J = A + B + C + D + E + F + G

5.2 每日消耗数组 cons[ ]

plan 维度: consPlan[d] = planValueOn(T0+d) // 销售计划逐日值，缺失→该SKU计划日均值，全无→0 avg 维度: consAvg[d] = round( mean( 近30日实际销量 ) ) // 全周期同一扁平均值

5.3 每日到货数组 inbound[ ]

inbound[d] = Σ { e.qty | e ∈ 已勾选阶段, e.etaDays == d, 0 ≤ etaDays < 100 } // 仅 SH_CHK[阶段]=true 的阶段参与模拟（货物池勾选项）

5.4 100 天逐日滚动模拟（simulateSmart）

balance[0] = max(0, 0 + inbound[0] − cons[0]) balance[d] = max(0, balance[d−1] + inbound[d] − cons[d]) // 结余钳制为 0，永不为负 firstStockout = min{ d | balance[d−1] + inbound[d] − cons[d] < 0 } // 首次本应破 0 的那天；若全程不破则为 null

balance 为钳制后结余（黄线）；firstStockout 是「真实缺货日」，用于算可售天数。

5.5 输出指标

X1 = Σ_{d=0..99} consPlan[d] // 计划维度 100天总消耗 Y1 = Σ_{d=0..99} consAvg[d] // 实际维度 100天总消耗 X2 = Σ_{d=0..N−1} consPlan[d] // 计划维度 前 N 天消耗 Y2 = Σ_{d=0..N−1} consAvg[d] // 实际维度 前 N 天消耗 Q1 = X1 − J // 计划维度 100天缺货（负=充足） S1 = Y1 − J // 实际维度 100天缺货（负=充足） Q2 = balancePlan[N] // 计划维度 第 N 天结余（钳制） S2 = balanceAvg[N] // 实际维度 第 N 天结余（钳制） replenishPlan = Σ_{d=N..99} max(0, consPlan[d] − (balancePlan[d−1] + inbound[d])) // N天后补货量·计划（按日缺口累计） replenishActual= Σ_{d=N..99} max(0, consAvg[d] − (balanceAvg[d−1] + inbound[d])) // N天后补货量·实际 coverPlan = max(0, −min_{d≥N}( Σ_{k=N..d}(inbound[k]−consPlan[k]) )) // 最小覆盖补货量·计划（第N天一次性补货的最少量） coverActual= max(0, −min_{d≥N}( Σ_{k=N..d}(inbound[k]−consAvg[k]) )) // 最小覆盖补货量·实际 sellableDays = (firstStockout === null) ? null : max(0, firstStockout − 1) // 可售天数；null = ∞（永不低于0） totalSales = (dim=='plan') ? X1 : Y1 totalShort = (dim=='plan') ? max(0,Q1) : max(0,S1)

「N天后补货量」 vs 「最小覆盖补货量」：前者按日累计第 N 天后的每日缺口（更贴近真实分批缺货），是生成需求单的默认基数；后者假设第 N 天一次性补一笔、之后不再破 0 的最小量，通常更小，可作保守参考。

5.6 导航与筛选

9.1 输入契约（Input Contract）

9.2 算法（Algorithm）

function computeSmartReplenish(sku):
  A = netStock(M3, sku, 'amazon')                 // +inbound −outbound +adjust
  B = netStock(M3, sku, 'pl')
  C = sum(arrivals(M4, sku))                     // 头程未结剩余量(结单/异常不计)
  D = netStock(M3, sku, 'logistics')
  E = netStock(M3, sku, 'supplier')
  F = sum(poPending(M2, sku))                    // 进行中PO未收量
  G = sum(reqApproved(M5, sku))                 // 已通过需求单合计
  J = A + B + C + D + E + F + G

  events = [ {stage:'A',qty:A,eta:0}, {stage:'B',qty:B,eta:LT.transfer3pl},
             ...C各事件..., {stage:'D',qty:D,eta:sea+portIn},
             {stage:'E',qty:E,eta:3+sea+portIn}, {stage:'F',qty:F,eta:?},
             {stage:'G',qty:G,eta:N} ]
  events = events.filter(e => checkedStages[e.stage] && 0<=e.eta <100)

  for dim in ['plan', 'avg']:
    inbound = zeros(100); for e in events: inbound[e.eta] += e.qty
    cons    = (dim=='plan') ? planDailyArray(sku,100) : actualDailyArray(sku,100)
    balance = zeros(100); firstStockout = null
    for d in 0..99:
      prev = (d==0)?0:balance[d-1]
      net  = prev + inbound[d] − cons[d]
      if net < 0 && firstStockout==null: firstStockout = d
      balance[d] = max(0, net)
    X = sum(cons);  Xn = sum(cons[0..N-1])
    replenish = sum_{d=N..99} max(0, cons[d] − ((d==0?0:balance[d-1]) + inbound[d]))
    cover = max(0, −min_{d≥N} cumsum(inbound[d..] − cons[d..]))

  Q1 = X_plan − J;  S1 = X_avg − J
  Q2 = balance_plan[N]; S2 = balance_avg[N]
  sellableDays = (firstStockout==null) ? null : max(0, firstStockout − 1)
  return { A..G, J, X1,Y1,X2,Y2, Q1,S1, Q2,S2,
           replenishPlan, replenishActual, coverPlan, coverActual,
           sellableDays, firstStockout, chart }

9.3 输出契约（Output Contract）

Output = {
  A,B,C,D,E,F,G, J,                 // 数量（件）
  X1,Y1, X2,Y2,                     // 100天/前N天 总消耗
  Q1,S1, Q2,S2,                     // 缺货 / 第N天结余
  replenishPlan, replenishActual,   // N天后补货量（建议下单基数）
  coverPlan, coverActual,           // 最小覆盖补货量（保守参考）
  sellableDays,                     // 可售天数；null = ∞
  firstStockout,                    // 首次缺货日索引；null = 不缺
  chart                            // 趋势 SVG 字符串
}

9.4 复刻检查清单

  • ✅ 库存结余必须 钳制为 0（max(0,·)），否则缺口会跨日累积成「债务」，违反业务含义；
  • ✅ replenish 只统计 d ≥ N 的缺口，N 天内的缺口不计入补货量；
  • ✅ 实际维度用「近 30 日扁平均」而非增长率外推；
  • ✅ C 阶段排除 M4 运单 status ∈ {结单, 异常}，按「运单总量 − 已入仓」比例分摊；
  • ✅ G 阶段只取需求单 status == '已通过'；
  • ✅ 日期统一用本地日期（避免 UTC 偏移导致逐日映射错位）；
  • ✅ 导航剔除 sellableDays>30 或该维度值为空的 SKU。

10. 边界情况与工程约定

场景处理
某 SKU 无任何销售计划/实际cons 全 0 → 不消耗 → 不缺货，sellableDays=null（∞）
在库 + 在途已覆盖 100 天消耗Q1/S1 ≤ 0，replenish=0，表格显示「无需补货」，不生成需求单按钮
当天库存即耗尽firstStockout=0，sellableDays=0（红色告警）
取消某阶段勾选（货物池）该阶段不进入模拟与图（仅影响视图，不改 J 真值口径——J 在内部始终全算，勾选只影响 inbound 注入）
可售天数预测表字段缺失/损坏渲染用 try/catch 安全网，空数据显空态而非报错
SKU 编码非 11 位颜色/市场回退为空串，不报错
